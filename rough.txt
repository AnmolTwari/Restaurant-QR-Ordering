# Permanent Coding Standards — Restaurant SaaS

For every new feature, bug fix, refactor, and code modification in this repository, strictly follow these production-level engineering standards.

## 1. Architecture and Code Quality
- Use the existing unified Next.js App Router architecture with TypeScript, React, Tailwind CSS, Prisma, PostgreSQL, and pnpm.
- Follow current Next.js best practices and the repository's established conventions.
- Write clean, modular, maintainable, reusable, and strongly typed code.
- Keep files ideally under 300 lines when practical. Split large files by responsibility, but avoid unnecessary fragmentation.
- Never create monolithic components, API route handlers, hooks, services, or utility files.
- Separate concerns into reusable components, custom hooks, services, utilities, validation schemas, constants, and types where appropriate.
- Use clear naming, consistent error handling, and single-responsibility functions.
- Avoid duplicated logic, unnecessary abstractions, deeply nested conditions, and premature optimization.
- Prefer simple, readable solutions over clever or overly complex implementations.

## 2. Next.js and React Best Practices
- Use React Server Components by default.
- Use Client Components only when browser APIs, state, event handlers, or client-side interactivity require them.
- Add `"use client"` only at the smallest necessary component boundary.
- Keep database access, authentication checks, authorization, and sensitive business logic on the server.
- Never expose secrets, private environment variables, database credentials, or privileged operations to client-side code.
- Use appropriate server-side data fetching, caching, revalidation, loading states, error boundaries, and route-level error handling.
- Avoid unnecessary client-side fetching, duplicated requests, hydration problems, and avoidable re-renders.
- Follow accessible, responsive UI practices for mobile, tablet, and desktop.

## 3. API and Business Logic
- Keep Route Handlers focused on HTTP concerns: parsing requests, validating inputs, invoking business logic, and returning consistent responses.
- Move reusable business rules and complex workflows into appropriate service modules.
- Validate all untrusted inputs on the server using the project's existing validation conventions.
- Enforce authentication, restaurant membership, role permissions, and tenant isolation on every protected operation.
- Never trust client-provided user IDs, restaurant permissions, prices, payment amounts, or order totals.
- Use database transactions, constraints, and idempotency controls wherever required for data integrity.
- Handle concurrent operations and failure cases explicitly.
- Return appropriate HTTP status codes and safe, consistent error responses.
- Never expose database stack traces, secrets, tokens, or sensitive internal implementation details.

## 4. Database and Prisma
- Reuse the existing Prisma schema and database patterns.
- Keep database queries efficient, tenant-scoped, and appropriately indexed.
- Avoid N+1 queries and fetching unnecessary data.
- Use transactions for related operations that must succeed or fail together.
- Add migrations for legitimate schema changes; never rewrite applied migrations or reset the database without explicit authorization.
- Preserve historical orders, payment records, audit logs, and other important business data.
- Verify schema changes and migration compatibility before considering a database-related task complete.

## 5. TypeScript and Dependencies
- Prefer strict typing, explicit domain types, and safe handling of nullable or untrusted data.
- Avoid `any`, unsafe type assertions, ignored compiler errors, and disabled lint rules unless there is a documented, justified exception.
- Reuse existing utilities and dependencies before introducing new ones.
- Add a dependency only when it provides clear value and is compatible with the existing project.
- Remove dead code and unused imports introduced by your changes.
- Keep environment variable validation centralized and document new required variables in `.env.example` without including real secrets.

## 6. Preserve Existing Functionality
This project already includes:
- Authentication and restaurant onboarding.
- Restaurant membership and role-based authorization.
- Menu categories and menu items.
- Table management and secure QR token lifecycle.
- Public menus and dining sessions.
- Customer carts, orders, and order tracking.
- Kitchen Display System and order status history.
- Razorpay payment integration and webhook handling.
- Counter settlement, receipts, payment history, and reconciliation.

Before changing any existing functionality:
1. Inspect the relevant implementation and its dependencies.
2. Understand existing business rules and security boundaries.
3. Identify affected routes, components, services, types, database models, and tests.
4. Make the smallest safe change that solves the requirement.
5. Preserve existing behavior unless the requested change explicitly requires otherwise.

Do not rewrite working modules merely to match personal stylistic preferences. Do not introduce NestJS, a separate backend, or a superadmin panel.

## 7. Testing and Verification
After every meaningful code modification:
- Run `pnpm typecheck`.
- Run `pnpm lint`.
- Run relevant tests for the affected feature.
- Run `pnpm test --run` for the complete regression suite when practical.
- Run `pnpm build` before considering a substantial change complete.
- Validate Prisma schema and migrations when database-related changes are made.
- Add or update tests for new behavior, error cases, authorization, tenant isolation, and regression risks.

Never claim that a command or test passed unless it actually ran successfully. If a check fails, investigate and fix the issue where possible. Clearly report any remaining failure or environmental limitation.

## 8. File Size and Refactoring Rules
- Aim for files under 300 lines when practical, not as an inflexible limit.
- If a file becomes difficult to maintain, split it into cohesive modules based on responsibility.
- Extract reusable UI into components, browser behavior into hooks, business rules into services, and shared contracts into types.
- Keep related code discoverable and avoid creating excessive one-function files.
- When modifying a large existing file, refactor only the relevant area unless a broader refactor is necessary and safe.
- Preserve public interfaces and existing API contracts unless a change is explicitly required.

## 9. Required Workflow for Every Task
Follow this sequence for every feature or code modification:

1. **Inspect:** Review the project structure, relevant files, existing conventions, and tests.
2. **Plan:** Identify the smallest implementation approach and affected modules.
3. **Implement:** Make focused, modular changes consistent with this instruction.
4. **Verify:** Run relevant tests, type-checking, linting, and builds as appropriate.
5. **Review:** Check for regressions, duplicated logic, security problems, and unnecessarily large files.
6. **Report:** Summarize what changed, which files were affected, which commands actually passed, and any outstanding risks.

Do not stop after writing code if verification is possible. Do not silently skip checks or hide failures.

## 10. Final Delivery Format
At the end of every task, report:
- Features or fixes implemented.
- Important files created or modified.
- Architectural or database changes, if any.
- Tests and verification commands executed, with actual results.
- Known limitations, unresolved issues, or follow-up work.

**Final rule:** Apply these standards consistently to every new feature, bug fix, refactor, and code modification in this repository. Prioritize correctness, security, maintainability, and preservation of existing functionality over implementation speed.
